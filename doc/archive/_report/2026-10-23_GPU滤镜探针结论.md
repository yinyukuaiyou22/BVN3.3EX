# GPU 渲染模式下的滤镜事实 —— 真机探针结论

- 日期：2026-10-23
- 设备：`306383853300549`（vivo，Android）
- 运行时：`AIR 51.0.1.1`（`Capabilities.version = AND 51,0,1,1`）
- 舞台：`2342 × 1080`（device 2408×1080，左侧 66px 被系统占用；`stage.quality=MEDIUM`，`frameRate=24`）
- 实验台：`tools/Test/filter_probe/`（`FilterProbe.as` + GPU/CPU 双包 + `build_filter_probe.py` / `run_filter_probe.py`）
- 原始产物：`tools/Test/_report/filter_probe_gpu.json`、`filter_probe_cpu.json`

CPU 组是**正对照**：如果 CPU 组也看不到滤镜，说明探针本身无效，GPU 组的"看不见"就没有意义。

## 结论表

| # | 问题 | GPU 组 | CPU 组（对照） | 结论 |
|---|---|---|---|---|
| F1 | GPU 合成器是否渲染 `DisplayObject.filters` | **否**（A 格绿像素 0） | 是（绿像素 1130） | GPU 模式**完全不渲染滤镜**，不是"慢"、不是"降质" |
| F2 | `BitmapData.draw()` 是否包含源对象自身的 filters | **是** | 是 | 软件渲染器会把滤镜烘进结果 |
| F2b | 源对象 `alpha=0`（隐藏）时 draw 是否仍含滤镜 | **是**（绿像素 1094） | 是 | 隐藏不影响烘焙 |
| F3 | `draw()` 是否吃源对象的 `alpha=0` | 否（照样画出内容） | 否 | 可以用 alpha=0 隐藏源节点再烘焙 |
| F3b | `draw()` 是否吃源对象的 `visible=false` | 否 | 否 | 同上；但工程内仍优先用 alpha（帧脚本会读 visible） |
| F4 | 链式 `applyFilter`（glow → ColorMatrix）叠加 | 正确（内核青、外圈品红） | 正确 | applyFilter 在 GPU 模式下**可用且正确** |
| F5 | `draw()` 是否吃源对象的 `colorTransform` | 否 | 否 | 染色必须在代理位图上运行时镜像 |
| F6 | 源 alpha=0 + 每帧改内容，draw 结果是否跟着变 | **是**（红↔蓝逐帧跟随） | 是 | 不存在"滤镜缓存冻结"问题 |
| — | GlowFilter(blur 24, q1, strength 2) 的实际外扩 | ≈10–15px | 同 | 远小于 `1.5×blur=36`；且右/下比左/上厚约 5px |

## 对实现的四条硬性影响

1. **烘焙 = 一次 `draw()`，不要再 `applyFilter`。**
   `draw()` 已经把滤镜算进去了。若照原计划"draw 再逐滤镜 applyFilter"，每个滤镜会被叠加**两次**（双倍辉光、双倍模糊）。实测证据：`gPX=1094` 的绿色光晕只可能来自 draw 内部。

2. **`applyFilter` 仍然可用，降级为兜底开关。**
   保留 `FPROXY_MANUAL_FILTER=false`；若某天某机型 draw 不再带滤镜，置 true 走"临时 `target.filters = null` → draw → 手动 applyFilter → 还原"的老路。默认走快路径。

3. **pad 必须按实测比例算，不能按 `1.5×blur`。**
   blur 24 实测只外扩 10–15px（约 `0.5×blur`）。公式保守取 `ceil(blur × 0.8) + 6`，再叠 distance（DropShadow/Bevel）。而且实测**四边不对称**（右/下多 5px），pad 必须对称取大值，否则会啃边。

4. **`alpha=0` 是安全的隐藏手段，且不影响烘焙。**
   这也是选它而不是 `visible=false` 的实测依据（F3/F3b 两者 draw 都不吃，但 visible 会被帧脚本和 `GameState.setVisibleByClass` 读）。

## 与 Adobe 文档的差异（值得记一笔）

Adobe《移动设备 GPU 呈现》只写了"不支持滤镜"，没写 `draw()` 的行为。官方 AS3 参考对 `draw()` 的描述是"source 不带自身的 matrix / colorTransform / blendMode"，**没有提 filters**。实测结论：filters 会被包含。这条差异是本次方案能砍掉一半工作量的原因。

## 复现方法

```bash
python tools/Test/filter_probe/build_filter_probe.py      # 出两个 APK（gpu / cpu 正对照）
python tools/Test/filter_probe/run_filter_probe.py gpu cpu
```

判定条件：`valid_red_blocks=true`（红块都在）+ CPU 组 `F1_filters_rendered=true`（对照组能看见辉光）。这两条不成立时，GPU 组的结论一律不可信。

## 已知坑（做探针时踩过的）

- ADT 打包会把 `<id>` 前缀成 `air.`，所以 `application.xml` 里要写 `com.bvn.filterprobe`，实际包名才是 `air.com.bvn.filterprobe`。
- `aspectRatio=landscape` 不等于锁横屏，必须显式 `<autoOrients>false</autoOrients>`，否则 stage 会随设备转成竖屏。
- 设备左侧有 66px 系统区，**stage 原点不等于 screencap 原点**。探针画了 2px 品红边框做标定，别按 (0,0) 硬算。
- `run-as` 在部分 ROM 上会 `packagelist_parse failed: Operation not permitted`；日志改写到 `/storage/emulated/0/Android/media/<pkg>/` 后用 `adb exec-out cat` 读，最稳。
- Git Bash 会把 `/storage/...` 当本地路径重写，命令行里必须先 `export MSYS_NO_PATHCONV=1`。
- 采样别用固定单点：光晕很薄，差 5px 就落到全透明区。按"整格统计颜色像素数"判定才稳。
