# 主菜单排版 决策记录（decision log）

> 主题：主菜单从「对角线阶梯 + 子项插同一列」改为「左侧竖列 + 二级独立列」，并收敛菜单数据。
> 来源：2026-10-27 与用户逐轮问答（深挖强度）。每条 = 结论 + 理由；被否决的选项一并记下，避免以后重复讨论。

## D1 问题定性：只改排版，不动菜单条目

**结论**：本次只重做排版算法与锚点，菜单**条目内容/数量一律不改**。
**理由**：用户明确「只是排版」；条目增减会牵涉模式入口与新手引导，属于另一件事。
**否决**：合并观战项、删低频项、把「小队/单人」改成平铺模式名。

## D2 数据只有一份，`getDefaultMenu()` 是死兜底 → 改委托

**结论**：`GameInterface.getDefaultMenu()` 改为委托 `GameInterface.instance.getGameMenu()`。
**理由**：`launch.as` 无条件 `GameInterface.instance = new GameInterfaceManager()`，且全仓只有这一个 `IGameInterface` 实现 ⇒ 静态兜底列表（无 EXIT、无换人、OPTION 无子项）**运行时永远不会被使用**。它比活列表更旧，谁只改它就会「改了没反应」，是典型的静默陷阱。
**否决**：删掉该方法（`IGameInterface` 契约仍要求实例提供 `getGameMenu()`，删静态方法收益小、易漏调用点）；只加注释（留着就会继续误导人）。

## D3 不做「平台能力开关」

**结论**：不引入 capability 对象，两端共用同一份条目与同一套排版。
**理由**：① 两端本来就吃同一份 `getGameMenu()`；② `AdManager.showVideoAd()` 是**空实现**，「更多游戏」在两端都只是空按钮；③ `EXIT GAME` 调 `NativeApplication.exit()`，PC 同样可用。当前**没有真实的平台差异需求**，加开关属于凭空造分支。
**否决**：按平台隐藏 EXIT / 隐藏广告位；「不要开关但删掉空按钮」（属于改条目，被 D1 挡下）。
**后续**：将来真要接广告或平台专属项，再在 `getGameMenu()` 里按 `GameConfig.TOUCH_MODE` 生成，不必先造框架。

## D4 行距：x 不再递减，竖向保留 5px

**结论**：一级列 `x` 恒定；行距沿用现有 5px（`MenuBtn.height + 5`）。
**理由**：用户澄清「无按钮之间的偏移」指的是**不再每行 x−40**，不是要贴紧。美术按钮本身带上下透明边距，5px 视觉上已是分开的；归零会让点击区相贴、误触率上升。
**否决**：行距归零；改成固定 8px（会与 `height=75/55` 的既有节奏打架）。

## D5 统一列宽 + 左缘对齐 + 文字靠左

**结论**：按列内最宽标签算列宽（`max(文字宽) + 2×16`），同列按钮等宽、左缘对齐、文字距左缘 16px；允许 `bg.width` 拉伸 `mc_wzbtn` 美术。
**理由**：左缘对齐 + 统一宽度才能让两列看起来像表格，碰撞计算也退化成「矩形区间不重叠」；文字继续居中的话左缘整齐反而更显参差。
**风险与退路**：`mc_wzbtn` 是 SWF 美术，拉宽可能拉花渐变/边框 → `setWidth(0)` 一个开关即可退回「各自宽度 + 左缘对齐」。
**否决**：各自宽度仍居中（左缘参差）；改 SWF 做真 9 宫格（成本不成比例）。

## D6 子列避让：整列跟随父项，越界整列上移

**结论**：子列 `y` 从父项 y 起向下排；若底端越界，**整列上移**并夹进 `[MARGIN_TOP, 600-MARGIN_BOTTOM]`；不做逐项微调。
**理由**：整列上移能保住列内行对齐（表格感），实现只需一次 clamp；逐项微调会破坏行对齐、且每加一项都要重算。
**否决**：允许单行上下微调；「先上移，放不下再开第二列」（当前最多 7 个子项，420px 一定放得下，开第二列是过度设计）。

## D7 导航保持上下单维

**结论**：不加左右键切列，不加鼠标悬停即展开；触屏语义不变（首点预览、再点确认/展开）。
**理由**：PC 的左右键与手柄摇杆左右是「移动」，占用会与游戏内手感冲突；展开后焦点直接进入子列、`back` 收回父列已经够用。
**否决**：左右键切列；悬停即展开（PC 上鼠标划过会连环展开）。

## D8 锚点：先按左边距 24、顶部 100

**结论**：一级列左缘 `MARGIN_LEFT=24`、顶 `MARGIN_TOP=100`（逻辑像素，800×600 坐标系）；跑起来再调常量。
**理由**：`title.swf` 左侧是否有 logo/立绘、`btnct` 是否带位移都还没有实测数据，先给一个保守值，看到真实画面再改数值比盲调靠谱。
**已知代价**：TOUCH_MODE 下 `MenuBtnGroup` 自身 `scale=1.1`，视觉左缘 ≈26.4px，可接受，不为它做补偿。

## D9 菜单挂 `_ui` 顶层，不再挂 `btnct`

**结论**：`MenuState.showBtns()` 把菜单直接 `_ui.addChild`，绝对定位；`btnct` 只打日志记录是否存在。
**理由**：`btnct` 的 transform（x/y/scale）未知且可能被 title 动画驱动，把菜单塞进去会让「靠左 24」变成一个无法静态推导的补偿公式（`(24 - ct.x)/ct.scaleX`），且一旦动画介入就会漂移。菜单要的是**稳定锚点**。
**退路**：若实机发现 title 动画确实依赖 btnct 一起位移，改回 btnct + 偏移补偿（各 3 行）。

## D10 删除滚动逻辑（`moveScroll`）

**结论**：删掉 `moveScroll()` 及 `_startPoint`、`_btnHeight`、`build()` 里的 `y-=40 / y+=30` 补偿。
**理由**：滚动是为「一条长阶梯」服务的：一级 6×80=480、二级最多 7×60=420，都小于可用高度（600−100−40=460 对一级、对二级 460），**当前根本不需要滚动**；留着它反而会在新布局里算出错误的位移。子列真溢出时用「行距压缩到 0.6× → 仍溢出则允许溢出并打日志」兜底。

## D11 入场动画改为从左缘滑入 + 淡入

**结论**：`fadIn()` 从「逐按钮 `scaleX: 0.01→1`」改为「`x: target−20 → target` + `alpha: 0→1`」。
**理由**：缩放原点在按钮中心，左对齐后会在动画期间把左缘推到更左，视觉上「先抖一下再对齐」；滑入 + 淡入没有原点问题，也不改变最终位置。

## D12 主菜单组在手机端不再整体 ×1.1；`MARGIN_TOP` 取 80

**结论**：`MenuBtnGroup` 构造时 `scaleX = scaleY = 1`（原来 TOUCH_MODE 下取 `SetBtnGroup.TOUCH_SCALE = 1.1`）；`MARGIN_TOP` 取 80。
**理由**（这是排完版算出来的硬约束，不是口味问题）：
- 一级 6 项 × (75 + 5) = 480 逻辑像素；×1.1 得 528 视觉像素，再加顶部边距必然突破 600 高。
- 旧版之所以能「看起来正常」，是靠 `y -= 40` / `y += 30` 的位移 hack + `moveScroll()` 整组滚动把它糊过去。
- 新布局要求位置可静态推导，所以尺寸必须可算：`80 + 6×80 = 560 = 600 − MARGIN_BOTTOM(40)`，正好用满安全区，两端同一套数值。
- 按钮不会小到难按：800×600 会等比放大到设备屏（1080p 横屏约 ×2.4），75 逻辑像素 ≈ 180 设备像素。
**否决**：保留 1.1 但把 `MARGIN_TOP` 压到 50（会顶到标题 logo）；按缩放比做坐标换算（解决不了行高膨胀，只是把同一个问题换个写法）。
**副作用**：手机端按钮比旧版小 9%，属于本次排版的可见变化。


## D13 菜单条目与导航的唯一改动点（2026-11-18 补记）

**结论**：改主菜单条目/导航，只改这两处，别的地方改了不会生效：

| 要改什么 | 改哪里 |
|---|---|
| 菜单有哪些项、顺序、二级子项（含 CAMERA CFG） | `mob/GameInterfaceManager.as` 的 `getGameMenu()` |
| 某个 label 点下去跳到哪个页面 | `ui/MenuBtnGroup.as` 的 `getFucByLabel()`（label → func 的 switch） |
| 一级/二级按钮怎么摆、锚点、列宽 | `ui/MenuBtnGroup.as` + `ui/MenuBtn.as` |

**理由**：用户 2026-11-18 原话「这才是管菜单排版的，索引里要是没写明白就写上，旧版PC的那个已经没用了都」。
`GameInterface.getDefaultMenu()` 只是委托到 `getGameMenu()`（见 D2），旧 PC 那套独立 option 列表整体作废，任何人都不要再往那里加东西。


## D14 TEAM 子项放不下 → 三级级联（2026-11-21）

**结论**：`MenuBtnGroup` 由「只支持一层展开」改为**层级栈**（`_openLevels`）：一级列 → 二级列 → 三级列从左往右紧排，`back` 逐层回退，`hoverBtn`/`render` 只作用在最深一层。TEAM PLAY 改成 4 项分组：

    TEAM PLAY
     ├ ARCADE          模式 10 闯关
     ├ VS   →  PEOPLE(11) / CPU(12) / WATCH(13)
     ├ DUO  →  DUO(14) / WATCH(15)
     └ TAG  →  TAG(16) / VS CPU(17)

**为什么不是两列网格**（本次先做、又被实测推翻的方案，记下来避免重复讨论）：二级项 2026-11-12 提到 80 高后，TEAM 8 项单列 = 680 > 可用 480，于是先试「一列拆两列」。按真实字形量（`tools/Test/assets/font/font1.xml`，size 35、字距 −8）：`TEAM DUO WATCH` 宽 **344px**、`TEAM TAG VS CPU` 325、`TEAM VS PEOPLE` 291；父列宽 253（`SINGLE PLAY` 221+32）⇒ 二级列可用宽只有 **487**，两列各需 376、合计 **764**，放不下。运行时日志原文：`[MENU] child grid skipped: need=764 avail=487` → 退回单列 `[MENU] child column overflow n=8 h=664 gap=3 cols=1`。结论：800×600 + 这套位图字体下，**这块区域没有「两列」的解**。

**否决的其它路**：① 行高压到 55（8×60=480 刚好）——与 2026-11-12「二级同字号同高」的修复冲突，中文副标题会被切；② 二级列滚动——D10 已删滚动，触屏手感差；③ 二级标签去 `TEAM ` 前缀凑两列——最长仍需 269/列，两列 550 > 487，仍不行。

**实测几何**（真实字形宽）：L1 宽 253（x 24..277）、L2 宽 182（x 289..471，标签 ARCADE/VS/DUO/TAG）、L3 宽 179（x 483..662，最长 PEOPLE=128）⇒ 右缘 662 ≤ 776；高度 L2 四行 335、L3 三行 250，都在 480 内。

**代价**：VS / DUO / TAG 三组模式各多一次点击；二级标签去掉 `TEAM ` 前缀（层级本身已表达归属）。
